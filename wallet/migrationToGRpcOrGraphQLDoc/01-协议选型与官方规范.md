# RTD TypeScript 前端的 gRPC、GraphQL 选型与官方规范

> 调研基准：2026-09-24 在线核对的 Sui Foundation 文档和 Mysten Labs TypeScript SDK 2.0 文档；本地源码核对对象为 `rtd-ts-sdk` 当前工作树。本文中的“官方事实”描述 Sui 的接口与官方建议；“RTD 推论”依据题设的同规格 fork 关系给出设计建议，不代表已验证 RTD 主网、FullNode、GraphQL、归档服务或 RPC 提供商的部署状态。

## 1. 先给结论：协议选型由调用目的决定

**官方事实。** Sui 的[数据接入决策矩阵](https://docs.sui.io/develop/accessing-data/data-serving)将 GraphQL 作为前端、仪表盘和灵活查询的良好默认选择，将 gRPC 作为后端、索引器、实时订阅和性能敏感型客户端的良好默认选择，并允许同一应用同时使用两者。[JSON-RPC 迁移总指南](https://docs.sui.io/develop/accessing-data/json-rpc-migration)进一步指出：只需读取一个 FullNode 的当前状态时，gRPC 通常足够；跨资源过滤、深分页或合并多个来源的读取，更适合 GraphQL。

**官方事实。** Mysten Labs 的 [TypeScript SDK 2.0 JSON-RPC 迁移指南](https://sdk.mystenlabs.com/sui/migrations/sui-2.0/json-rpc-migration)从 SDK 使用角度建议大多数应用代码先迁至 `SuiGrpcClient` 的顶层方法；需要自定义索引查询、历史对象版本或自定义选择集时使用 `SuiGraphQLClient`。其[客户端总览](https://sdk.mystenlabs.com/sui/clients)同时明确两者都是正式支持的主要选择，且共享常规客户端方法，包括交易和事件历史查询。因此，“GraphQL SDK 已存在”不能推出所有调用都该改为 GraphQL；“SDK 推荐 gRPC 默认”也不能推出钱包历史页面应放弃 GraphQL。

**RTD 推论。** 对 `link-u-mobile`、`rtd-apps/wallet` 等 TypeScript 应用，建议将**交易与低延迟当前状态路径**优先设计为 gRPC，将**丰富的历史展示和组合查询路径**设计为 GraphQL；超出 FullNode 保留期的已知数据详情另接归档能力。最终默认客户端需按该应用实际调用分布、运行时兼容性和可用 RTD 服务来定，而非按“前端”这一标签统一决定。

## 2. 两套官方文档为何看起来相反

**官方事实。** [Sui 数据接入接口总览](https://docs.sui.io/develop/accessing-data/data-serving)是面向系统架构和查询工作负载的选择表，故将“前端、仪表盘、灵活历史查询”放在 GraphQL 栏。[Mysten SDK 客户端总览](https://sdk.mystenlabs.com/sui/clients)及[SDK JSON-RPC 迁移指南](https://sdk.mystenlabs.com/sui/migrations/sui-2.0/json-rpc-migration)是面向现有 TypeScript 调用点的升级路径，故将 gRPC 作为**没有特殊查询需求时**的默认客户端。这是建议范围的差异，不能忽略其中任一方。

**RTD 推论。** 可采用“一个业务能力可以由不同传输实现”的 SDK Core API 作为隔离层，应用按页面或服务的需求选择实际客户端。可复用的 RTD SDK 内部接受 `ClientWithCoreApi` 并调用 `client.core`；应用代码调用具体 `RtdGrpcClient` / `RtdGraphQLClient` 顶层方法。该分层来自 [SDK Core API 官方规范](https://sdk.mystenlabs.com/sui/clients/core)与[SDK 构建规范](https://sdk.mystenlabs.com/sui/sdk-building)，本地 `packages/typescript/src/client/`、`src/grpc/`、`src/graphql/`、`src/jsonRpc/` 已有对应结构。此处只说明源代码形态，不宣称三种传输在 RTD 网络均已可达。

## 3. GraphQL、Indexer、FullNode 与 Archival 的实际关系

**官方事实。** [GraphQL RPC 官方架构](https://docs.sui.io/develop/accessing-data/graphql/graphql-rpc)包括 General-purpose Indexer、Postgres 兼容数据库、近期状态用的 Consistent Store、可选 Archival Service 和 FullNode。索引表负责按地址、类型等条件查找；归档负责旧交易、对象和检查点点查询；GraphQL 服务把交易**执行与模拟**交给 FullNode。由此，Indexer 可承担读模型，不能单独替代执行、模拟及 FullNode 低延迟当前状态职责。[数据接入接口总览](https://docs.sui.io/develop/accessing-data/data-serving)亦将这些组件列为不同能力。

**官方事实。** [FullNode gRPC 修剪说明](https://docs.sui.io/develop/accessing-data/json-rpc-migration)规定 FullNode 仅服务于自身数据保留窗口；较早数据可能返回 `not found`，没有旧 JSON-RPC 某些路径曾有的隐式归档回退。Archival Service 是另一项 gRPC 服务，提供交易、对象和检查点的未修剪**点查询**，不提供交易执行或完整当前状态 API。GraphQL 只有在部署方配置归档后，才可对受支持的旧数据点查询统一路由。[归档服务概览](https://docs.sui.io/develop/accessing-data/archival-store)确认归档的职责是跨过 FullNode 和索引数据库常见保留窗口。

**RTD 推论。** 对钱包的历史详情页，应由数据服务运营方或应用后端负责配置“GraphQL + Archival”或“FullNode gRPC + Archival gRPC”的路由、保留策略与服务等级；前端不应把一次 FullNode `not found` 直接展示成“链上从无此交易”。如果还要按条件搜索索引保留期以前的数据，需持续保留相应索引或建设业务索引。具体保留天数、归档覆盖范围和查询可用性必须在 RTD 环境实测，不能从 Sui 生产节点的运营配置推断。

## 4. 浏览器、React Native 与服务端运行时

**官方事实。** [TypeScript SDK gRPC 客户端文档](https://sdk.mystenlabs.com/sui/clients/grpc)指出默认 `GrpcWebFetchTransport` 通过 Fetch API 在浏览器和 Node.js 中工作，使用 gRPC-Web 协议；另有只面向 Node.js、Bun 等服务端的原生 gRPC transport。因此“浏览器不能用 gRPC”不成立，但浏览器使用的是 gRPC-Web，不等于原生 gRPC transport。该文档还介绍了服务端流及取消方法，说明 SDK 层支持相关调用。

**RTD 待验。** 上述官方文字没有给出对当前 `link-u-mobile` 所用 React Native 版本、Hermes、iOS/Android Fetch 流式响应的完整兼容性保证。前端采用 gRPC 前应分别在目标浏览器和 iOS/Android 真机验收：gRPC-Web endpoint 与代理路径、CORS/预检（浏览器）、TLS、超时与取消、普通请求、列表流、订阅重连和回补。若移动端流式能力不稳定，可让后端运行原生 gRPC 订阅并向移动端提供适合其运行时的推送或查询接口；这是一种部署设计建议，并非对当前 RTD 环境的既成判断。

## 5. 基础交易文档解决什么问题

**官方事实。** 用户提供的 [Building Transactions](https://sdk.mystenlabs.com/sui/transactions/basics)讲的是 `Transaction` 如何构建 PTB、Move 调用、Coin 操作及 `build({ client })` 如何解析对象版本、Gas 和意图；其示例可传 `grpcClient`。该页不负责决定全部读取接口的协议，也没有证明 GraphQL 不可用于交易执行。交易执行属于[独立的 SDK 执行说明](https://sdk.mystenlabs.com/sui/clients/executing)：两类客户端都提供执行、模拟和等待能力，且链上执行失败会以 `FailedTransaction` 判别分支返回，Promise 正常完成不代表业务交易成功。

**RTD 推论。** 对现有前端，应先保留 PTB 构建与签名的业务意图，按传输改造解析输入及提交所用客户端，并验证钱包签名、Gas 选择、成功状态和执行后读取。迁移不能简单把 `Transaction` 类或 `tx.moveCall()` 的存在理解为“已完成 RPC 迁移”。

## 6. JSON-RPC 迁移不是换构造函数

**官方事实。** [SDK 2.0 迁移指南](https://sdk.mystenlabs.com/sui/migrations/sui-2.0/json-rpc-migration)列出的典型对应关系包括：`getTransactionBlock → getTransaction`、`queryTransactionBlocks → listTransactions`、`queryEvents → listEvents`、`dryRunTransactionBlock → simulateTransaction`、`getOwnedObjects → listOwnedObjects`（仅精确 `StructType` 可直接映射）。旧交易/事件查询默认倒序，而新 `listTransactions`、`listEvents` 默认正序；需要保留旧页面顺序时必须显式传入 `order: 'descending'`。[Sui 迁移总指南](https://docs.sui.io/develop/accessing-data/json-rpc-migration)强调 JSON-RPC 游标不能沿用到新协议，应以新 API 重新取游标。

**官方事实。** 一些迁移无一对一顶层方法：复杂对象过滤需自定义 GraphQL 或应用索引；动态字段与动态对象字段要分别处理；多笔交易按 digest 查询可逐笔调用顶层 `getTransaction`，若确需 wire 层批量能力可使用原始 gRPC 服务；旧 `unsafe_*` 构造方法要改为 PTB。具体筛选差异和转换见 [SDK 方法映射](https://sdk.mystenlabs.com/sui/migrations/sui-2.0/json-rpc-migration)及[链级方法映射](https://docs.sui.io/develop/accessing-data/json-rpc-migration)。

**官方事实。** 新版顶层方法的参数和结果形状也发生变化，例如 `showEffects` 等旧 `options` 改为 `include`，交易结果用 `$kind` / `Transaction` / `FailedTransaction` 判别。[SDK Core API](https://sdk.mystenlabs.com/sui/clients/core)还明确：GraphQL 的 `getTransaction` 一次 `include.events` 最多提供前 50 个事件；GraphQL 读取的索引可能落后于执行，应使用 `waitForTransaction`；gRPC 过滤查询即使一页为空，也可能继续返回 `hasNextPage: true`。这些都是迁移验收必须覆盖的语义差异。

**RTD 推论。** 建议为每个原 JSON-RPC 调用登记：业务用途、旧方法及过滤、目标方法/传输、响应字段映射、排序与游标、历史保留要求、写后读取时序、运行时和接口契约测试。旧 JSON-RPC 客户端可作为短期过渡；其最终退出计划应根据 RTD 的实际节点和网关发布节奏制定。Sui Foundation [2026 年 JSON-RPC 停用时间表](https://docs.sui.io/develop/accessing-data/json-rpc-migration)只是 Sui 自营节点的运营事实，不能直接当作 RTD 已执行的关闭日期。

## 7. 依赖版本和本地源码的裁决顺序

**官方事实。** Sui 官网迁移总指南的生态工具段落仍描述旧 `@mysten/dapp-kit` 仅用 JSON-RPC、旧 Kiosk SDK 尚不能接收 gRPC；但 [Mysten 2.0 dApp Kit 专项迁移文档](https://sdk.mystenlabs.com/sui/migrations/sui-2.0/dapp-kit)清楚区分旧包与新的 `@mysten/dapp-kit-react`，后者 `createClient` 示例直接创建 `SuiGrpcClient`。[Mysten 2.0 Kiosk 专项迁移文档](https://sdk.mystenlabs.com/sui/migrations/sui-2.0/kiosk)也明确新包接受 `ClientWithCoreApi`，支持 gRPC 与 GraphQL。两组描述并存时，应以**实际安装包版本、该版本源码和专项迁移文档**裁决，不能摘取旧生态工具段落作为当前所有包的限制。

**本地已核事实。** 当前 `rtd-ts-sdk/packages/typescript/package.json` 的包名为 `rtd-typescript`，版本字段为 `2.31.3`，提供 `./grpc`、`./graphql`、`./jsonRpc`、`./client`、`./transactions` 导出；源码可见 `RtdGrpcClient`、`RtdGraphQLClient`、`RtdJsonRpcClient`，后者被标注废弃。`packages/typescript/src/grpc/client.ts` 默认创建 `GrpcWebFetchTransport`。这些仅证明 SDK 代码路径存在；RTD FullNode 是否暴露相匹配的 gRPC、GraphQL 查询/执行后端是否完整、是否配置 Archival、是否已停止 JSON-RPC，均需单独核验。

## 8. 生产上线前必须取得的证据

以下是**RTD 建议验收项**，不是对现网能力的宣称；[官方迁移指南](https://docs.sui.io/develop/accessing-data/json-rpc-migration)也明确公共 Sui 负载均衡 URL 有限流，生产钱包或索引器应使用自营或专用服务商端点。

1. **端点能力**：记录 RTD 各网络 gRPC-Web、原生 gRPC、GraphQL、Archival 的独立 URL、认证方式、TLS、CORS、限流及是否允许交易执行。
2. **当前状态与执行**：用测试钱包验证余额、对象、Gas、模拟、签名、提交、执行成功/失败、`waitForTransaction` 与写后读取；应用不得将网络请求成功误当链上成功。[SDK 执行语义](https://sdk.mystenlabs.com/sui/clients/executing)。
3. **历史覆盖**：选取 FullNode 保留窗口内外各一笔已知交易、对象版本和检查点，分别验证 gRPC FullNode、归档 gRPC、GraphQL 的结果；另验证索引保留窗外的按地址交易检索。[官方归档分工](https://docs.sui.io/develop/accessing-data/json-rpc-migration)。
4. **跨传输一致性**：核对列表排序、过滤、分页、事件数量、对象 BCS 内容和 GraphQL 索引延迟；图形界面需要对“已执行但尚未索引”给出明确状态。[SDK Core API 差异](https://sdk.mystenlabs.com/sui/clients/core)。
5. **客户端运行时**：在 `rtd-apps/wallet` 目标浏览器与 `link-u-mobile` 真机分别验证常规 Fetch、gRPC-Web、流式响应、取消和重连；若未实际执行，不应记为兼容通过。[SDK gRPC transport 说明](https://sdk.mystenlabs.com/sui/clients/grpc)。
