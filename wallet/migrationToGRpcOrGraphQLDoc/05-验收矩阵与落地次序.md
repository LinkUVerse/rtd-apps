# 迁移验收矩阵与落地次序

核对日期：2026-09-24。此文件是实施验收计划，不是已通过的测试报告。截至本次文档工作，未修改 `link-u-mobile`、`rtd-apps/wallet` 的业务代码，也未对 RTD 服务做真机、浏览器扩展或归档端到端验收。只有实际执行且记录结果的条目才能标记“通过”。

## 1. 交付次序与阻塞关系

| 阶段                | 交付与责任                                                                                                                               | 完成证据                                                                                   | 下一阶段门槛                                              |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------- |
| A. 网络及依赖基线   | 链运营方记录 `temp/rtd` 与 SDK commit、创世 digest、目标网络、每种协议端点与保留期；前端锁定 `rtd-typescript` 2.31.3 对应 workspace 版本 | `getServiceInfo` / `getChainIdentifier`、GraphQL `chainIdentifier`、部署配置及实际请求响应 | 服务可用性不靠仓库存在推断；两个前端不能使用 Sui 公网 URL |
| B. gRPC live 路径   | 链运营方提供 Full Node gRPC-Web/TLS/CORS；移动端和扩展完成连接试验；前端改造交易、余额、模拟、当前状态                                   | dev 环境真实交易摘要、签名字节、链上效果、iOS/Android/Chrome 日志                          | 支付恢复与失败/未知结果用例通过，链身份与服务端订单一致   |
| C. GraphQL 索引路径 | 链运营方启动 Indexer、数据库、GraphQL，公开 schema/限流/索引高度；前端迁移地址活动与历史详情                                             | 固定 checkpoint 的历史查询、分页、对象版本与 GraphQL 索引水位                              | 首屏/翻页无漏单重单，写后读有明确 pending 状态            |
| D. 归档与长历史     | 链运营方接入独立 Archival Service 并定义 Retention/SLA；业务方确定多年地址活动的索引方案                                                 | 已修剪交易 digest、旧对象版本、旧 checkpoint 点查；超保留期过滤查询的可用证据              | 产品要求的历史窗口完整，归档不只“代码存在”                |
| E. 灰度与移除旧协议 | 前端统一关闭 JSON-RPC 适配层；链运营方观察零旧请求，再停用旧服务                                                                         | 埋点、网关日志、错误率、客户版本覆盖和回滚预案                                             | 确认无生产依赖后才能停旧接口；RTD 时间表独立制定          |

这些阶段可在开发环境并行准备，但**上线门槛不可跨越**。Sui Foundation 的 JSON-RPC 停用日期是上游运营事件，不是 RTD 自动生效日期；RTD 应按自身调用存量和替代服务验证结果决定停用。[官方数据接入总览](https://docs.sui.io/develop/accessing-data/data-serving)、[官方迁移时间表](https://docs.sui.io/develop/accessing-data/json-rpc-migration)。

## 2. 服务就绪验收

| 检查               | 最小实测                                                                                                                                                  | 失败时的责任与处理                                                                                                 |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| RTD 链身份         | 同一网络的 Full Node gRPC `GetServiceInfo.chain_id`、SDK `getChainIdentifier()`、GraphQL genesis digest 与旧 `checkpoint 0.digest` 一致；不同网络确实不同 | 链运营方纠正端点/创世配置；前端拒绝跨网络复用签名字节、订单与游标                                                  |
| Full Node gRPC-Web | 从实际 Chrome 扩展页面/Service Worker、iOS、Android 分别读当前余额与 getTransaction，再模拟并提交测试交易；检查 TLS、CORS 预检、响应头和超时              | 网关/节点运营方修 gRPC-Web；移动端如仍不可用再选签名后后台转发方案，禁止私钥上送                                   |
| GraphQL 基础       | 通过正式 URL 请求 `chainIdentifier`、`serviceConfig`、近期地址活动、分页及对象版本；记录索引 checkpoint 与 Full Node 高度                                 | Indexer/GraphQL 运维方修 ingestion、schema、限流或端点；前端不得以空结果代表确实无交易                             |
| GraphQL 执行依赖   | 验证查询正常时 Full Node 暂不可用的行为，以及执行/模拟必须调用 Full Node 的链路；配置故障告警                                                             | 不能把纯 Indexer 当作执行后端；按 [官方架构](https://docs.sui.io/develop/accessing-data/graphql/graphql-rpc)修接入 |
| Archival           | 构造或保留一组已离开 Full Node 保留窗的固定 digest、对象 ID+版本、checkpoint，分别从 Full Node、归档 gRPC、带归档 GraphQL 查询；核对原始内容/校验摘要     | 归档运营方补齐摄取、服务、回填及监控；GraphQL 运维方确认 `ledger-grpc-url` 真正指向具所需保留范围的服务            |
| 长期条件筛选       | 查询超出通用 Postgres 索引保留期的指定地址/事件/对象活动，检查结果和分页完整性                                                                            | 产品/数据平台决定延长索引保留或建业务索引；Archival 的点查不能自动补齐任意历史筛选                                 |
| 限流与故障         | 以预期并发、页大小、GraphQL 查询复杂度测试 429、超时、网络闪断、切换网络；记录 p95/p99 和错误率                                                           | 运营方设容量与告警，前端退避/分批/取消旧请求；阈值依据负载测试确定，不在文档中虚构 SLA                             |

Full Node gRPC 无隐式归档回退、GraphQL 只有在配置 Archival 后才可能承担读取旧详情，这两项是[官方明确边界](https://docs.sui.io/develop/accessing-data/json-rpc-migration)。官方建议常规 GraphQL Postgres 索引保留 30–90 天，但这只是成本与功能的起点，RTD 的钱包历史窗口须由产品要求和实际运营保留策略决定。[GraphQL 留存建议](https://docs.sui.io/develop/accessing-data/graphql/graphql-rpc)。

## 3. 前端功能回归矩阵

| 场景           | Link-U Mobile                                         | Chrome 钱包                                                               | 必须核对的结果                                                                                    |
| -------------- | ----------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 新客户端与依赖 | `RtdGrpcClient`、共用 Core API、React Native/polyfill | gRPC/GraphQL 客户端、`rtd-dapp-kit-react` provider/hooks、`rtd-apps/core` | 安装与 TypeScript 构建成功；无旧 `RtdClient` 类型/导出和旧 dApp Kit 顶层目录引用                  |
| 当前资产       | 原生 RTD、各币种余额、coin 分页与交易 gas             | 地址余额、owned objects、NFT/coin、动态字段                               | 数值单位、大小整数、对象归属、分页覆盖数与旧环境固定样本一致；不能只比首屏                        |
| 交易构建/模拟  | 单笔 RTD 支付、资料单笔/批量交易、Move returnValues   | 钱包转账、dApp 签名、dry-run                                              | PTB bytes/digest、gas 选择、模拟返回值、链上失败与成功分支均按新类型处理                          |
| 交易提交与恢复 | 网络超时、应用被杀、重启、服务端确认延迟、订单过期    | MV3 Worker 重启、提交超时、网络切换                                       | 使用保存的同一签名和 digest 查证；未知状态不创建第二笔付款；链 ID 不一致拒绝广播                  |
| 活动和风控     | 收入/支出/赞助/对象变更、多个分页、刷新               | 活动页、收据页、zkLogin 历史判断、目标地址风险提示                        | 先定义 `affectedAddress` 的产品语义；固定历史样本无漏单、重单，旧 cursor 不复用                   |
| 写后读         | 交易刚提交而 GraphQL 尚未摄取                         | 收据/资产刷新发生索引延迟                                                 | live 路径证明链上状态，UI 显示待索引并按策略重试；不因 GraphQL 暂空重新交易                       |
| 旧历史         | 已修剪 digest 详情、旧对象版本、批量记录              | 老收据/老账户活动与搜索                                                   | Archival 点查可用；超索引窗口的列表由产品索引承担，未部署时显示真实“历史不可查询”状态而非伪装为空 |
| 异常与安全     | gRPC error code、网络闪断、服务端幂等确认             | GraphQL `data+errors`、429、CORS/CSP、受限权限                            | 无私钥外传；错误分类正确；清除跨网络缓存；限流不诱发重复签名/广播                                 |

验收必须包含真实设备与插件运行时。单纯 SDK 单元测试或 `tsc` 通过不能证明浏览器扩展 Service Worker 的 gRPC-Web 请求、React Native 的 Fetch 传输、RTD GraphQL 索引及归档链路正常。[gRPC Web transport 官方说明](https://sdk.mystenlabs.com/sui/clients/grpc)只明确浏览器和 Node.js，未承诺所有 React Native 环境；因此真机证据是移动端上线门槛。

## 4. 对照样本与分页方法

准备一组**同一 RTD 创世下**的固定测试账户和 checkpoint 范围：本人发出、收到、为他人赞助 gas、对象状态变化、Move 调用、失败交易、跨 checkpoint、超过 50 个事件的交易、同一时间戳多笔交易、已修剪交易、旧对象版本。对每一条记录保存 digest、checkpoint、sender、affected address、balance changes、status 和预期 UI 分类。金额与余额使用整数/BigInt 比较，不以浮点或屏幕文案比对。

对活动列表先对照协议定义：旧 `FromAddress + ToAddress` 双列表与新 `affectedAddress` 不一定同集，后者可包含 sponsor 或由状态变化关联的地址。产品必须选择期望集合；若要精准保留旧两路业务语义，使用 GraphQL/原生 gRPC 查询或应用索引补足，并明确双游标、合并排序、digest 去重及收敛边界。分页测试须遍历到结束；gRPC 某页即使为空且 `hasNextPage=true` 仍要前进。[官方 SDK 查询映射](https://sdk.mystenlabs.com/sui/migrations/sui-2.0/json-rpc-migration)、[Core 页行为](https://sdk.mystenlabs.com/sui/clients/core)。

对旧历史应分别证明：① 已知 digest 可点查；② 对象旧版本可读；③ 按地址或事件过滤能覆盖所承诺的最老日期。①② 通过不代表③通过，因为归档点查不提供任意多年条件搜索。[官方归档服务](https://docs.sui.io/develop/accessing-data/archival-store)、[GraphQL 保留策略](https://docs.sui.io/develop/accessing-data/graphql/graphql-rpc)。

## 5. 监控、灰度与回退

上线前定义并仪表化：Full Node gRPC 可用率/错误码/尾延迟、交易提交未知结果数、确认耗时、GraphQL 索引 checkpoint 与链 tip 差值、查询部分错误数、索引最老 checkpoint、Archival 摄取水位与最老可查记录、长历史查询失败率、前端 CORS/预检失败、旧 JSON-RPC 请求数。阈值应来自负载试验和业务要求，并附具体告警责任人。

按内部账户 → 测试版移动端/扩展 → 小比例用户逐级灰度。协议切换开关应以网络和调用类别为粒度；回退到旧 RTD JSON-RPC 只在它确实仍部署且旧功能已回归时可用。付款恢复必须独立于协议开关：已签名/已广播交易始终用原网络、原订单、原 digest 查询，不能因回退或重试构建新付款。

**关闭 JSON-RPC 的签收条件**：迁移后的两前端及 `rtd-apps/core` 编译通过；上表关键业务流真机/插件验收通过；长历史保留方案符合产品承诺；网关连续观测期内旧协议请求归零（观测期由 RTD 运营方定）；故障回退方案和用户版本覆盖完成。未满足这些条件前只可宣布“方案已完成”或“局部代码已迁移”，不能宣布“生产迁移完成”。
