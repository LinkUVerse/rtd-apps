证据分三类：

1. **源码事实**：文件里的导入、调用、类型和方法定义。这说明迁移工作量和预期编译契约。
2. **依赖安装状态**：`node_modules` 中当前解析到的包。它可能与包清单或源码版本不同，不能代表重新安装后的结果。
3. **运行验证**：本次未执行。TLS/CORS、gRPC-Web、React Native fetch、索引覆盖率、历史留存、扩展权限、交易确认时序仍须环境验收。

统计方法：扫描非 `*.test.*`/`*.spec.*` 的 `.ts`/`.tsx` 文件，统计显式 `client`、`rtdClient`、`rpc` 或 `fullNode` 变量上的旧 SDK 方法调用。动态接收者、`useRtdClientQuery`、`api.instance.fullNode` 和间接 hook 不计入，所以数量是**可复核的下界**，不是全仓所有链调用总数。

新版 SDK 的准确导入形式：

```ts
import { RtdGrpcClient } from 'rtd-typescript/grpc';
import { RtdGraphQLClient } from 'rtd-typescript/graphql';
import { RtdJsonRpcClient } from 'rtd-typescript/jsonRpc'; // 仅迁移过渡

const grpc = new RtdGrpcClient({ network: 'mainnet', baseUrl: grpcWebUrl });
const graphql = new RtdGraphQLClient({ network: 'mainnet', url: graphqlUrl });
const legacy = new RtdJsonRpcClient({ network: 'mainnet', url: jsonRpcUrl });
```

证据：`N/packages/typescript/src/grpc/index.ts:4`、`graphql/index.ts:4-15`、`jsonRpc/index.ts:10-18`、`client/index.ts:4-34`；构造参数分别在 `grpc/client.ts:27-35,140-166`、`graphql/client.ts:47-55,117-138`、`jsonRpc/client.ts:103-120`。`/client` 只导出 Core/Base/类型等，**不再导出旧 `RtdClient`**；其已构建的 `S/packages/typescript/dist/client/index.mjs:1-6` 也没有该导出。相反，Wallet 当前旧缓存 `W/node_modules/rtd-typescript/dist/cjs/client/index.js:22` 仍将 `RtdClient` 映射为旧 JSON-RPC client。这是“包清单、新源码、旧缓存”必须分开叙述的直接证据。

新 SDK 的三个具体客户端都提供 `client.core` 的统一 Core API，同时保留各自的原生能力。`N/packages/typescript/src/client/core.ts:37-116` 定义统一契约；`grpc/client.ts:140-166` 与 `graphql/client.ts:106-138` 创建对应 Core。JSON-RPC 类已标记 deprecated，见 `jsonRpc/client.ts:94-106`。这并不表示所有旧方法都能无改动调用：新版参数名与返回结构有实质变化。

### dApp Kit 的变化是单独的迁移项

Wallet 在 `W/src/ui/index.tsx:17,102-126` 使用旧 `RtdClientProvider`；大量界面使用 `useRtdClient` 或 `useRtdClientQuery`，例如 `W/src/ui/app/hooks/useGetAllBalances.ts:4-17`。新 React 包的导出在 `N/packages/dapp-kit/packages/dapp-kit-react/src/index.ts:4-15`：`createDAppKit`、`DAppKitProvider`、`useCurrentClient`、`useDAppKit` 等，没有这些旧 hook/provider。新 Core 包 `.../dapp-kit-core/src/core/index.ts:61-77` 要求 `createClient(network)` 返回兼容 Core API 的客户端，`.../core/types.ts:4-9,31-60` 明确了该契约。Wallet 是**钱包扩展本身**，还包括后台签名器、消息协议和账户状态；新 dApp Kit 的接入不能替代它自己的扩展签名/授权逻辑。建议把其 React 数据访问迁到新 provider/hook 或本项目兼容层，并单独检查钱包与外部 dApp 的协议兼容。

## 5. 与新 Core API 对照后发现的主要缺口

| 旧 JSON-RPC 调用/返回                                                                              | 新 Core API 与源码                                                                                                                                                                                                                                                                  | 具体风险/推荐处理                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `new RtdClient({url})`                                                                             | `/client` 不再导出旧类；三协议各自构造且要求 `network`，见第 2 节。                                                                                                                                                                                                                 | 在 Mobile/Wallet 入口建立网络配置及客户端工厂；过渡期仍需 JSON-RPC 时显式导入 `/jsonRpc`。不要用同一个 URL 猜三个协议。                                                                                                                                                                                                                                                                                                     |
| `queryTransactionBlocks({filter:{ToAddress/FromAddress}})`                                         | Core `TransactionFilter` 仅有 `sender` 与 `function`：`N/packages/typescript/src/client/types.ts:489-511`；三协议 Core `listTransactions` 都按此契约，GraphQL 映射只写 `sentAddress/function`：`graphql/core.ts:646-685`，gRPC 映射只写 `sender/moveCall`：`grpc/filters.ts:7-42`。 | **只将历史列表改成 `client.core.listTransactions({filter:{sender}})` 会漏掉收到的转账**。GraphQL 原生 schema 已有 `affectedAddress`（`graphql/generated/schema.graphql:4366-4378`），gRPC 原生 proto `TransactionFilter` 有 `affectedAddress`（`grpc/proto/rtd/rpc/v2/filter.ts:69-78`），但当前 RTD Core 封装未暴露。可增加经过测试的 Core 通用过滤器、使用原生 GraphQL 查询，或提供后端历史 API；需确认索引包含全部历史。 |
| 两个收/发查询共用 cursor、单页显示                                                                 | Mobile `.../blockChainWalletScreen/index.tsx:90-126` 共用一个 cursor；Wallet `.../useQueryTransactionsByAddress.ts:17-52` 未翻页。                                                                                                                                                  | 对流水完整性建立验收：多页、同一交易同时属于收/发、无时间戳、索引延迟、修剪期之后重查。原生 GraphQL `affectedAddress` 可把两条流变一条，但它的语义是 sender/sponsor/recipient，需按业务展示筛选余额变化。                                                                                                                                                                                                                   |

## 6. 迁移优先级与验收边界

**P0：先让依赖和运行时契约一致。** 将 Mobile/Wallet 的旧 `RtdClient` 导入改为明确的新版客户端，Wallet 同步处理 `rtd-dapp-kit` 拆包与 `rtd-apps-core` hooks。基于当前 `S` 源码重新安装、构建后记录解析到的实际包路径和版本。此时的编译成功只说明类型层走通，不说明链服务可用。

**P1：建立交易执行通道。** 签名继续在客户端本地完成；交易构建所需链查询、模拟、提交、近期确认优先接 gRPC-Web/Core（以设备/扩展兼容性和 RTD 服务端支持为前提）。保留 Mobile 现有“签名前核对网络、先持久化原始字节/签名/摘要、未知结果只查原摘要”的恢复规则。用户业务的服务端确认仍由现有服务端订单 API 承担。GraphQL 可以提供查询，但不应成为签名器的唯一提交路径。

**P2：建立历史通道。** 活动列表、回执/交易详情、zkLogin 历史判断和地址风险提示首先明确所需覆盖期与数据字段；使用已确认留存和同步延迟的 GraphQL/索引服务或自己的后端历史 API。近期结果可先由 gRPC 获取；已修剪详情由独立归档 Ledger gRPC 或接好归档的 GraphQL 点查，按 digest、网络 ID 与 checkpoint 去重、校验一致性。索引缺失/延迟必须与“从未发生”区分。`affectedAddress` 语义及收/发方向需从余额变化和交易数据中再推导。

**P3：真实环境验收。** 分别在 Android/iOS、Wallet 扩展弹窗与后台、各 RTD 网络验证：TLS/CORS/gRPC-Web；切换网络和自定义节点；coin/NFT/Kiosk 分页；大于一页且跨修剪期的历史；交易广播未知后的同字节恢复；GraphQL 同步落后时回执不误报失败；旧订单 `networkId` 与新 `getChainIdentifier()` 一致。未运行的这些验证不能写成“通过”。

结论：从**现有前端源码**看，链状态/交易执行的优先迁移目标可以是 gRPC-Web/Core，但历史收发地址列表和修剪后的详情需要持久索引服务。GraphQL 原生查询有相应过滤能力；当前统一 Core API 尚未暴露该能力。这是协议分工与 SDK 封装的实际缺口，不能由“把 `RtdClient` 全部替换成 `RtdGrpcClient`”自动解决。
