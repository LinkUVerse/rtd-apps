## 2. 两条路线的同范围比较

| 维度 | A：在原项目整体替换 RPC 层 | B：冻结后新建功能等价钱包 |
| --- | --- | --- |
| 新 RPC 与端点工作 | 三客户端、协议桥接、网络／类型／分页／签名映射均需要 | 同样需要，没有天然减免 |
| 页面与账户基础 | 直接保留，通过新领域 DTO 接入 | 重新构建或复制并适配；复制后仍承接旧债务 |
| 安全回归面 | 核心是新 RPC 与交易边界，保留已存在的账户安全结构 | 新账户库、权限、通信、恢复、导入等都需重新证明 |
| SDK 包迁移 | wallet 与共享 core 都要改 | 复制原组件同样需要；重写则增加 UI 成本 |
| Chrome 身份／存储 | 保留插件 ID，做受控配置／journal schema 迁移 | 新 ID 时旧库隔离，需安全迁移或重新导入；复用 ID 仍存在覆盖和回滚问题 |
| 两套产品成本 | 基准归档，只有一个活动实现和发布流水线 | 若旧项目继续运行，会增加双构建、双测试和版本说明；真正永久冻结才可避免 |
| 历史债务 | 可删除旧 RPC，保留非 RPC 部分经验证的资产 | 新文件名不能消除复制来的旧类型、SDK 调用和行为假设 |
| 服务运维 | 三逻辑入口、一个入口治理方案 | 相同服务需求；新钱包不会减少 HBase／PG／Fullnode 组件 |
| 推进可见性 | 按页替换、最终禁止旧调用，可逐批比对 | 容易在新登录／余额演示阶段停留，完整功能重建更晚暴露缺口 |
| 初步估算 | 23–38 人日 | 35–58 人日 |

估算成立条件：复用现有 UI 与普通账户模型；需要修改源码、执行本地链及 Chrome 验收；不要求复制官方钱包所有尚未在 RTD 落地的外部业务。复杂网络条件、质押缺失历史、多 epoch fixture 可能扩大量。工期与人日不同，多人并行会增加合并和同链验收协调成本。

## 3. 推荐 A 的具体形态

### 3.1 改动位置

在原仓库新增小而明确的模块，名称为建议，非现有代码：

```text
wallet/src/shared/rpc/
  network-profile.ts       配置、身份、能力与修订
  clients.ts               Fullnode / GraphQL / archive 客户端构造
  identity.ts              同链检查、dev 重建处理
  policy.ts                操作到端点的明确路由
  errors.ts                传输错误与领域状态
  domain.ts                钱包领域 DTO；不复制整套旧 JSON-RPC 类型
wallet/src/ui/app/rpc/
  WalletRpcProvider.tsx    React 生命周期、取消与实例绑定
  queries/                显式 TanStack 查询、key 与分页
  transaction/            新执行映射与既有 journal 衔接
core/src/api/             复用并整理原生 GraphQL 读取／领域组合
```

共享 core 用显式传入的 `ClientWithCoreApi`／读取接口；应用调用具体客户端的顶层方法。不要向旧 `RtdClient` 塞入任意对象制造假兼容，也不要令所有组件知道三个 URL。

### 3.2 允许的破坏性替换

- 从单 URL 配置升级为网络三入口配置；旧配置无法自动识别 gRPC 时要求重新确认。
- 更换所有旧 JSON-RPC 返回 DTO；保留 UI 的展示模型，写显式转换。
- 移除旧 dApp Kit 读取 Hook，以钱包自己的 Provider 和 TanStack Query 替代。
- 完成后移除发布路径中的 `/jsonRpc`、JSON-RPC Transport、自动 fallback 与旧类型 shim。
- 调整内部事件／queryKey／状态 schema；用一次性迁移脚本与 fixture 测试，不维持长期双读。

### 3.3 保留但重新验证的边界

账户库、助记词派生路径、签名 Intent、密码加密与导出验证、站点权限、Chrome 扩展身份、钱包注入协议和视觉交互。新数据层不能顺便修改这些安全合同。RPC 层确需修改它们时，应作为单独可审核的工作包，并补齐对应测试。

## 4. 基准冻结与回滚设计

**实施开始前**完成，本文未执行冻结：

1. 记录 SDK、wallet/core、主链及归档源码、锁文件、构建工具、链／合约 fixture 的版本。
2. 同时保存 wallet 与 core 的已跟踪和未跟踪源码；现有未提交改动不能被 stash／reset 丢弃。以审阅后的 Git 提交或独立归档保存，记录文件哈希。
3. 排除 `.env`、账户库、助记词／私钥、浏览器 Profile、node_modules、dist、Docker 卷和运行时凭据；基准源码归档不能成为密钥备份。
4. 对关键页面、权限和交易成功／失败／未知行为建立可重放参考；记录测试结果与未支持项。
5. 保持单一活动钱包实现与明确的当前试用网络。历史源码基准只读保存；网络换代、旧 pending 隔离、完整回放等验收确需另一套链／数据层时，按独立目录、端口、H0／generation 和资源清单隔离，记录保留原因，验收后清理失去用途的环境。不能仅按进程同名杀掉必要的对照服务。
6. 账户与 journal 升级须可恢复：新 journal 与旧 schema 分离、保留旧记录；回滚旧版本前阻止其重复执行新的 pending digest。

回滚是发布包与配置回退，不是删除新 journal、自动恢复旧发送流程或清除账户库。若旧 JSON-RPC 服务已经停用，回滚钱包包也不能恢复网络能力；优先修复新版本或暂停执行，不能把“退旧包”当作保证。

## 5. 何时改选 B

只有在基准实证中发现以下问题，才重新决定新建：账户／权限架构本身无法满足安全需求，或者在保持现有 UI 时核心网络逻辑几乎不可分离，且实测切片显示适配成本超过重新实现。

目前没有足够证据支持这些条件。当前源码具备明确 client 构造、background signer、query hooks 和 recovery 边界，更适合按层替换。缺少新 SDK 顶层质押方法、归档浏览器传输或账户历史完整性，不是新建钱包自动解决的理由。
