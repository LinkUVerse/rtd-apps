# NET-11：跨会话／窗口读取预算实施前设计

2026-10-05。父任务保持开放，49/98，trial_ready=false。上一批当前钱包产物及签名证据在本批改动后只作历史证据；必须重新构建及核验。

现有单WalletReadSession的4运行／64等待名额不能限制UI窗口、后台准备／恢复及独立准入的合计。采用两层保守限制：同一JS上下文所有会话共用4个运行／申请名额、64个FIFO等待名额；同一扩展storage bucket所有窗口与worker共用4个固定名字的原生Web Locks物理读取名额。名字不包含账户、端点或其他配置，所有binding共用，避免切网或重建会话扩大旧请求仍占用时的总并发。

每个叶请求同时申请4个exclusive名额，首次获锁的回调同步认领，取消其余尚未获锁的申请，只有赢家执行读取。锁持有到原操作promise完整结束；调用方取消不提前释放忽略取消的底层操作。等待使用原有会话／调用方截止信号，获得锁前取消零传输；获得锁后迟到结果仍由session屏障拒绝。错误、取消、失败均回收上下文名额。禁止steal、query后判断占用或租约过期放行。ExecuteTransaction本身不加入读取排队或重试；辅助身份／验签／模拟继续经已有叶包装。

Web Locks缺失时拒绝读取，不默默回退到无共享限制。原始浏览器锁异常保留取消原因；不可用使用固定公开错误。单上下文FIFO不承诺多个上下文的严格全局FIFO。64是每上下文等待上限，跨窗口等待总数随存活上下文数增加；它不是全浏览器总等待64或服务端配额。不同Chrome profile、隐身bucket、设备及非钱包客户端不共享此限制。退出上下文自动释放Web Locks不证明服务端已停止旧计算，取消传播仍属ENV-05／06剩余验收。

依据：[W3C Web Locks Working Draft 2025-09-24](https://www.w3.org/TR/2025/WD-web-locks-20250924/) §2.2、§2.6、§3.2.1：同bucket页面与worker共享管理器，等待请求可取消，已获锁后acquisition signal不释放锁，callback promise终结才释放；这是草案与本地Chrome能力，不能表述为Sui限额或分布式服务器fencing。
